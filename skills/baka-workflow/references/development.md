# 开发与交付

## 工作目录和记录

- 沿用当前聊天选定的目录，不额外强制 worktree。在该目录发出的明确修改指令，视为对任务范围内修改的授权，不再追加“允许修改主工作区”的确认；这不授权覆盖他人改动或未请求的破坏性 Git 操作。
- 写入前确认目录、分支、目标文件和已有改动归属；不得覆盖、回退、stash 或混入他人改动。已有改动阻塞 checkout／merge 时保留现场，改用指定基线的干净目录。
- 仓库开发首次写入前，创建或复用仓库约定的 work record，原始输入逐字保存到 `prompt.md`；改变目标、范围或验收的后续输入逐字追加，纯控制指令不追加。记录与本轮任务改动一起提交。仓库外用户级配置或环境操作不套用仓库 work record。
- Plan／Spec 按可独立验证、可独立提交的行为拆任务，写清目标、涉及文件或模块、依赖和验收方式；不要求每项单独提交，不增加额外确认或子代理。

## 调试和评审

- 修复前确认现象、复现条件和相关变更，提出根因假设，用最小实验逐一验证；无法复现先补证据，连续修复失败重新查根因，避免叠加补丁。简单问题直接判断并修复，不另写文档或增加确认。
- 评审检查需求符合性、相关调用链与边界、回归风险及关键行为的验证覆盖。仅报告有依据且可行动的问题，按严重性排序，注明位置、触发条件和影响；无发现就明确说明。只读评审不自动转为修改。

## 提交和推送

- 每轮结束前提交本轮仓库改动，包括代码、文档、已确认的计划或任务记录；验证失败也提交。无改动不创建空提交，不要求每个子任务立即提交。用户明确要求不提交时遵从，提交受阻就说明原因，不擅自绕过钩子。
- 提交信息用 `type(scope): subject` 概括用户任务和本轮改动；原文在 `prompt.md` 中，不重复全文，不加 AI 协作者标记。
- 普通提交用 `git commit --only -- <显式路径...>`；新文件先 `git add <显式路径>`，不清理或改动他人 index。
- active merge 不能路径级提交；全部冲突解决、仅 stage 冲突文件和本任务记录、完成聚焦验证后创建标准 merge commit。
- 提交后立即用 `git show --stat <sha>` 核对范围；发现夹带非任务内容时停止后续 Git 操作并报告，不自行 reset、revert 或 amend。

验证结果与 commit 分开判断；无论失败程度如何，仍按上面要求保存本轮提交。push 按下表决定：

| 验证状态 | push |
| --- | --- |
| 已执行且通过 | 默认允许 |
| 未执行／主动跳过 | 说明跳过项和原因，允许；不声称通过 |
| 已执行但非阻塞失败 | 说明失败、影响和不阻塞的依据，允许 |
| 已执行且阻塞失败 | 保留本地提交，禁止 push，报告问题 |

阻塞失败包括本轮改动造成核心流程不可用、构建失败、安全或数据完整性问题，以及未满足关键验收要求。非阻塞失败须有证据，例如已确认的无关历史失败，或不影响交付的非关键检查失败；无法判断影响时先查明再 push。失败不能改称跳过，未运行、被环境阻断的检查也不能声称已经通过。仓库强制检查和权限约束仍须遵守。

允许 push 时，首次 `git push -u origin <branch>`，之后 `git push`，不 force push。Code MCP 无 push 接口时可用普通 git push，不为工具替换再询问。用户要求仅本地、不 push 或暂不发布时不推送，也不创建远端 MR。

## MR／CR

- 允许远端交付时，默认创建或更新当前任务的 Code MR，复用已有 MR，优先 Code MCP；能力或权限不足就说明，不重复创建。
- MR 目标先用当前任务明确指定值，其次用本机 AGENTS.md 的项目表，再查仓库约定和远端默认分支，仍不明确才询问；确认目标存在，已知且有效的目标不重复确认。
- 缺陷任务按项目约定创建或复用 AOne CR，将修复方案、CR 和 MR 回填同一缺陷评论。先查本机项目特例；明确免除 CR／Bug／回填的项目只走 MR。不为没有缺陷上下文的普通修改新建缺陷。
- 报告真实验证状态；有跳过项或非阻塞失败时不把 MR 描述成“全部通过”。推送不代表授权合并或发布。
